# Skill doctor

A skill that never triggers costs exactly as much as a skill that does not exist, and it fails silently — no error, no log line, just a model that solves the problem its own way while your carefully written instructions sit unread. Most reviews of a skill therefore need to start with the description, not the body.

## Run the linter, then read the skill

```bash
python3 scripts/lint_skill.py path/to/skill/
python3 scripts/lint_skill.py path/to/skills/ --recursive   # a whole folder
python3 scripts/lint_skill.py path/to/skill/ --json         # for CI
```

Exit codes are 0 clean, 1 warnings, 2 errors, so it drops into a pre-commit hook or a pipeline without wrapping.

The linter catches what is mechanically checkable: missing or malformed frontmatter, descriptions too short to match on or long enough to be a permanent context tax, bodies past the progressive-disclosure guideline, references to `scripts/…` that do not exist, and bundled files nothing points at. What it cannot judge is whether the instructions are any good — that is the reading pass below.

## Diagnosing a skill that never triggers

This is the most common complaint, and it is almost always the description.

Claude sees only the skill's name and description when deciding whether to load it. If the description describes a *capability* rather than a *situation*, there is nothing for the model to match a user's actual request against.

| Symptom | What is usually wrong |
|---|---|
| Never triggers | Description names a capability, not the situations. "Helps with data processing" matches nothing anyone types. |
| Triggers only when named explicitly | Trigger phrases are missing — the description never says "use this when…". |
| Triggers on the wrong things | Description is broad enough to overlap a neighbouring skill. Name what it is *not* for. |
| Triggers, then the model ignores the instructions | Body problem, not description: too long, or it reads as background rather than a procedure. |

The rewrite that fixes most of these: keep the first clause as the capability, then add a second half listing the concrete situations — including phrasings users would actually type, and cases where they describe the problem without naming the tool.

**Before:** `Helps with SQL queries and database work.`

**After:** `Review SQL for destructive or accidentally expensive behaviour before it runs against a real database — flags writes hidden inside CTEs, DELETE without WHERE, unbounded scans. Use this whenever SQL is about to touch a shared or production database, whenever a query was generated by an LLM and nobody has read it line by line, and whenever someone asks "is this query safe to run".`

Under-triggering is far more common than over-triggering, so lean toward being explicit and slightly pushy about when the skill applies. But do not pad: the description sits in context permanently, in every conversation, whether or not the skill is ever used.

## Reading the body

Once triggering is sorted, the questions are about whether the instructions actually help.

**Does the body earn its length?** Everything in SKILL.md loads whenever the skill triggers. Background the model already knows — what BPMN is, why SQL injection is bad — is pure cost. Detail that is needed sometimes belongs in `references/`, loaded on demand.

**Does it explain why?** Instructions that carry their reasoning survive situations the author did not anticipate; bare commands do not. A skill full of shouted MUSTs and NEVERs usually indicates an author who did not trust the reader — and the model reads reasoning better than emphasis. When you see six or more of these, look for the rule that could be one sentence of explanation instead.

**Is it a procedure or an essay?** A skill is read mid-task by a model that needs to do something next. Numbered steps, a table, a template — these are usable. Three paragraphs of context before the first actionable sentence are not.

**Is there a worked example?** One concrete input-to-output pair does more than a page of description, especially for anything with a specific output format.

**Would a script do it better?** If the skill describes a fiddly deterministic procedure in prose — build this XML, validate that structure, compute these numbers — the model will re-derive it every time, slightly differently. Bundle a script and point at it. A good signal: if three different runs of the skill would each write a similar helper, that helper belongs in `scripts/`.

## Structure worth checking

```
skill-name/
├── SKILL.md          name + description in frontmatter, instructions in the body
├── scripts/          deterministic work: run rather than re-derive
├── references/       detail loaded only when needed
└── assets/           templates and files used in output
```

- Directory name and frontmatter `name` identical, lowercase-hyphenated.
- Every bundled file mentioned in SKILL.md, with a line about *when* to read it. An unmentioned reference file is invisible; a mentioned one that does not exist is worse, because the model will try to open it.
- Reference files over ~300 lines get a table of contents at the top.
- Scripts carry a module docstring with usage examples — that is how the model learns to call them without reading the source.

## Report format

Lead with the verdict on triggering, because that is the failure that makes everything else moot.

```
SKILL: <name>
TRIGGERING: good | weak | broken — [one line on why]

MUST FIX
1. [what, and what it breaks]

WORTH FIXING
1. [what, and what it improves]

SUGGESTED DESCRIPTION
[a concrete rewrite, not advice about rewriting]

WHAT WORKS
[what to keep — a review that only lists faults gets argued with]
```

Write the replacement description rather than describing what it should contain. A rewrite can be pasted; advice has to be re-derived by someone who has already shown they find this part hard.
