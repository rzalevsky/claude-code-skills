# SQL safety review

A query that reads fine at a glance can still write. `WITH t AS (DELETE FROM users RETURNING *) SELECT * FROM t` has `SELECT` as its root node and deletes the table. That single example is the reason this skill exists: **classifying SQL by its first keyword is not validation**, and every review here works on the whole parse tree instead.

This matters most in two situations. One: an agent or automation has a database connection, and something has to decide what it may execute. Two: a human is about to paste generated SQL into a production console. In both, the cost of a false negative is asymmetric — a wrongly blocked SELECT costs a retry, a missed DELETE costs a restore.

## How to run a review

**1. Parse before you read.** Run the bundled checker first, then read the query yourself. The script catches the structural cases mechanically; your reading catches intent.

```bash
python3 scripts/check_sql.py --file query.sql             # the normal case
python3 scripts/check_sql.py --file migration.sql --allow-write   # a deliberate write
python3 scripts/check_sql.py --file q.sql --json          # for a gate or a hook
python3 scripts/check_sql.py --file q.sql --force-fallback  # test the degraded path
```

Two practical notes. Paths here are relative to the skill directory — if your working
directory is elsewhere, use the absolute path. And pass real queries through `--file` or
stdin rather than as a shell argument: SQL is full of single quotes (`interval '90 days'`),
and shell quoting will mangle it in ways that change what you reviewed.

The script uses [sqlglot](https://github.com/tobymao/sqlglot) when it is installed and falls back to a conservative pattern scan when it is not. The fallback is deliberately noisier — it says so in its output, and in fallback mode an "OK" verdict is not evidence of safety. Install the parser when the answer matters: `pip install sqlglot`.

**2. Classify the intent — and check the blast radius the parser cannot see.** Ask what the author meant this query to do, then check whether the query does exactly that and nothing else. Most real incidents are not malicious SQL — they are a WHERE clause that matches more rows than the author pictured, or a join that silently multiplied them.

Four things worth tracing every time, because no parser will find them for you:

- **Side effects beyond the rows named.** Deleting `sessions` logs people out. A foreign key with `ON DELETE CASCADE` means the row count you were shown understates what disappears.
- **NULL exclusion.** `last_seen < now() - interval '90 days'` never matches NULL. If NULL means "never seen", the rows most relevant to the question are the ones silently dropped.
- **Result shape.** `RETURNING` on a join or a one-to-many gives one row per child, not per parent. Missing `DISTINCT` usually means nobody looked at the output shape.
- **Reversibility.** If this is wrong, what does recovery look like — an undo, or a restore from backup?

**When the SQL was written by a model, invert the usual charity.** The judgement calls below ask whether the author knew what they were doing; for generated SQL, assume nothing was intended. A model reaching for `DELETE ... RETURNING` as a convenient way to get a row set is a plausible accident, not a decision.

**3. Report findings by severity, not by line order.** A reviewer who lists ten style notes before the DELETE has buried the one thing that mattered.

## What to flag

**Blocking — do not run as written.**

| Pattern | Why it matters |
|---|---|
| Write node anywhere in the tree (INSERT/UPDATE/DELETE/MERGE), including inside a CTE | Root-keyword classification misses these entirely |
| `UPDATE` or `DELETE` with no `WHERE` | Affects the whole table; almost never the intent. Only distinct from the row above under `--allow-write`, where writes are expected but unqualified ones still are not |
| `SELECT ... INTO new_table` | Creates a table despite the SELECT root |
| DDL: `DROP`, `TRUNCATE`, `ALTER`, `CREATE` | Schema change, usually irreversible in place |
| `GRANT` / `REVOKE` | Permission change disguised as a routine statement |
| Multiple statements in one string | Classic injection shape: the second statement is the payload |
| `SET` / `SET SESSION` changing session behaviour | Silently changes semantics for everything that follows |

**Warning — run only with eyes open.**

| Pattern | Why it matters |
|---|---|
| `SELECT ... FOR UPDATE` / `FOR SHARE` | Takes row locks; blocks other transactions even though it reads |
| Unbounded scan on a table you cannot size | Fine on 10k rows, an outage on 10^9 — ask for the row count, do not guess |
| Cartesian product: join with no condition, or a comma join | Row count multiplies; often shows up as "the query never finished" |
| `WHERE` on a nullable column without NULL handling | `col != 'x'` drops NULL rows silently |
| String-concatenated parameters | Injection surface; recommend bound parameters |
| `DISTINCT` added to fix duplicate rows | Usually a symptom of the join being wrong, not a fix |

Not every warning needs to become a blocker. A `FOR UPDATE` inside a deliberate transaction is correct code. The judgement to apply: does the author appear to know this is happening?

## Report format

Keep it short enough to read before running the query. Anything longer than the query itself will be skipped.

```
VERDICT: BLOCK | WARN | OK
(parser: sqlglot 27.x | fallback pattern scan — verdict is not authoritative)

BLOCKERS
1. DELETE inside CTE `t` — the statement writes despite the SELECT root.
   Line 1: WITH t AS (DELETE FROM users RETURNING *)

WARNINGS
1. No LIMIT on `events` — unknown row count. Ask before running on production.

SAFE REWRITE
WITH t AS (SELECT * FROM users WHERE created_at < '2026-01-01' LIMIT 1000)
SELECT * FROM t;

WHAT CHANGED
The DELETE became a SELECT so the query can be inspected first. If deletion is
genuinely intended, run it inside an explicit transaction and check the count
before COMMIT.
```

**On a BLOCK verdict, say plainly that the query should not be run, and give the person the version they can run.** A review that stops at "this is dangerous" leaves someone under time pressure to make the call themselves, which is how the query gets run anyway. Offer both: the read-only rewrite that answers their question, and — if the write turns out to be intended — the safe shape for it, which is an explicit transaction with the row count checked before `COMMIT`.

When you propose a rewrite, say what changed and why in one or two sentences. A rewrite the author does not understand will be pasted without reading, which is exactly the failure this skill is trying to prevent.

## Enforcing this in a running system

Reviewing by hand does not scale to an agent making queries at machine speed. When the database sits behind an MCP server, a tool, or a workflow, put the same rules in the path — and put them in **two independent layers**, because a parser bug should not be the only thing standing between an LLM and a production table.

- **Layer 1, structural.** Parse the statement and walk the whole tree. Accept only what you can name: exactly one statement, of an allowed read-only type, with no write node anywhere inside it. Allow-list, never deny-list — a deny-list is a list of the attacks you have already thought of.
- **Layer 2, the database.** Run every query in a read-only transaction, on a role granted the minimum it needs, with a per-transaction `statement_timeout`. This layer holds even when layer 1 is wrong, which is the entire point of having it.

`references/postgres-patterns.md` has the concrete PostgreSQL mechanics — read-only transaction setup, timeouts, least-privilege grants, and the parser cases worth having tests for.

## Where this came from

The two-layer approach and most of the blocking list come from a working MCP server that exposes PostgreSQL to a language model: [github.com/rzalevsky/mcp-postgres-server](https://github.com/rzalevsky/mcp-postgres-server). Its security tests run without a database precisely so the parser boundary can be tested in isolation — a habit worth copying, since the parser is where the interesting failures live.
